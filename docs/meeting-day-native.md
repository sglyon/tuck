# Native meeting reminders

The Meeting Workspace core owns snapshot bounds, occurrence identity, five-minute due policy, sixty-second late grace, active-meeting suppression, dismissal, and durable delivery claims. Native code supplies the wall clock, read-only device calendar refresh, OS notification access, and delivery. It never joins a call or starts recording.

`runtime::compose` starts no reminder worker. Only the Tauri host explicitly calls `start_reminders` after composition. The diagnostic JSONL host has no notification backend or timer; `meeting_reminder_status` returns `available:false`, `permission:"unavailable"`, and `running:false`. Enabling through that host returns an understandable error without changing the preference or requesting OS access. Snapshot import and `get_meeting_day` remain testable there.

The default-off preference is `meetingReminders`. A disabled worker wakes every fifteen seconds only to read this raw preference from SQLite; it never reads credential flags, calendar authorization, or notification authorization. Enabled idle operation uses the core's cheap active-state guard. The worker skips calendar and notification work during recording, paused capture, and capture processing. It has one owned thread and an interruptible channel wait. Shutdown cancels before joining; helper execution and native callbacks are bounded. Dropping the worker also stops it. Repeated start is idempotent, and start/shutdown serialize through one ownership lock.

When opted in, the worker refreshes an already-authorized device calendar at most once every four minutes, reading the next seven days of events with the same bounded horizon as the UI. It never invokes calendar connection or permission requests. Failed/disconnected refresh invalidates device reminder freshness while preserving the bounded visible cache; failure does not prevent imported-calendar reminders. Failed refreshes share the four-minute interval. Device reminders require a snapshot refreshed within five minutes. Imported ICS snapshots remain eligible for their seven-day lifetime. EventKit excludes canceled events and the current user's declined invitations; both native and ICS paths carry `allDay` so the core can omit all-day reminders. Recurrence expansion for ICS remains unsupported.

Every tick claims the due batch durably before any delivery attempt, then coalesces it into one generic notification. Core due policy is evaluated again against a fresh wall clock before delivery. A final preference, active-state, and cancellation guard prevents deferred work after disabling, recording, or shutdown. Claims are never retried after failure or interruption. This intentionally favors an omitted notification over duplicate or old nags after a crash or sleep. OS presentation can be delayed or suppressed by Focus, system policy, foreground presentation rules, or the notification service itself; an accepted request is not proof that a banner appeared. In-app reminders remain useful when OS delivery is denied.

`meeting_reminder_status` returns `{available, permission, enabled, running, message}`. `set_meeting_reminders {enabled}` is the native preference entry point. Only its explicit enable operation requests notification permission; status and launch never do. The native generic `update_settings` route rejects this preference so it cannot bypass explicit notification access. Notification text contains only the app name and a generic meeting nudge, with no title, attendee, join link, occurrence key, or audio controls.

On macOS, authorization and delivery use maintained `objc2-user-notifications` bindings in the main app process. They are guarded by application bundle identity before calling UserNotifications; unbundled hosts return unavailable. Completion callbacks copy only enum/bool values and use bounded channels. Status/delivery wait at most four seconds; the explicit user authorization operation may wait sixty seconds. There are no native notification helpers with a different bundle identity.

On Windows/Linux, delivery uses the maintained Tauri notification plugin. Its desktop permission API always reports `Granted`, so Tuck deliberately reports `permission:"unknown"` instead of claiming it observed OS authorization. The enable command records the user's choice; these platforms have no reliable prompt/status contract through the plugin. System settings control delivery. Windows notifications require an installed application. This implementation was compiled and tested on macOS; Windows/Linux branches were checked against the maintained plugin API but were not executed on those operating systems.

Verification uses fake notification/calendar ports: disabled/active suppression, denial without prompts, durable claim before delivery failure, no duplicate attempt, canceled refresh, failed/disconnected calendar invalidation, refresh backoff, fresh clocks after sleep, overlapping-batch coalescing, idempotent start, and prompt shutdown. No personal calendar, microphone, actual notification authorization, or real notification delivery is used by these tests.
