# Tuck's public Notion connection

Tuck users choose **Connect Notion**, approve Tuck and selected pages in Notion's browser page picker, then return to Tuck. They choose a shared parent page and Tuck can create a complete standard meeting database, or they can select an existing database. They do not create integrations or copy tokens. The advanced token field remains available for existing installations.

## Flow and security boundary

Notion's documented exchange requires the public connection's confidential client secret. A small Cloudflare Worker performs that exchange; the desktop never receives that shared secret. The official protocol uses the [authorization code flow](https://developers.notion.com/guides/get-started/authorization). No undocumented Notion PKCE parameters are sent.

The native host creates a random verifier and sends its S256 challenge to `POST /v1/notion/start`. The Worker creates a random 256-bit transaction ID, also used as OAuth state, and returns the official Notion authorization URL. The fixed callback routes state to that transaction's Durable Object and accepts one result. Native polling submits the ID and verifier in a JSON body to `/complete`; proof validation atomically consumes the code before exchanging it. Tokens return only in the HTTPS response body. The browser receives a static page with no external resources, no reflected code, no redirect and `Referrer-Policy: no-referrer`.

Each transaction owns one SQLite-backed record: challenge, deadline and an optional authorization code or denial. It accepts no meeting data or saved credentials. Its five-minute deadline is checked on every read; an alarm removes unused records even when the user leaves. Consumption deletes the record before external I/O, so callback and completion replay cannot exchange twice. Cloudflare storage recovery remains subject to platform retention; application expiry is not a physical-erasure claim. A lost token-exchange response requires a new connection, because the server deliberately does not retain credentials for replay.

One Durable Object per transaction follows the actual coordination boundary and survives Worker isolate eviction. It avoids a global coordinator and an application database. Fixed input, code and provider-response bounds limit each record/request. Workers rate limit bindings protect expensive operations and polling by peer IP and aggregate keys. Their counters are per Cloudflare location and approximate; shared networks may be throttled. They are abuse controls, not a globally exact cardinality or billing cap. See [Durable Object storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/), [alarms](https://developers.cloudflare.com/durable-objects/api/alarms/) and [rate limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).

## Saved credentials and lifecycle

The OS keyring's existing `notion` entry atomically stores either a legacy manual token or a typed OAuth bundle. The bundle contains the original broker origin, access token, optional refresh token and minimal workspace metadata. No credentials enter SQLite, backups, status DTOs, webview state or logs. Status reads local presence and metadata only.

Before a publication or destination lookup, OAuth access is checked with the fixed Notion `users/me` read endpoint. Only an actual 401 triggers one serialized refresh. Both rotating credentials are saved atomically; a valid response with `refresh_token: null` remains usable and asks the user to reconnect if renewed access is later needed. A changed broker origin requires reconnecting. No ambiguous content write is automatically retried. The broker's refresh/revoke endpoints require possession of an existing token and contact only fixed Notion endpoints. See [refresh](https://developers.notion.com/reference/refresh-a-token) and [revocation](https://developers.notion.com/reference/revoke-token).

Cancel, repeated connect, manual replacement and disconnect advance the native session generation. A stale connection or refresh cannot overwrite the newer decision. A private, credential-free OS file lease gives one native host control of the shared keyring entry across independent windows/processes; another host can read status but receives a clear busy error on credential use/mutation. The lease releases when the owner exits. Disconnect deletes the local keyring entry first, then attempts Notion revocation; a failure truthfully asks the user to remove Tuck in Notion Connections. A browser consent that completes after cancellation can still leave a grant in Notion; the desktop does not save it. Already-authorized publication requests may finish after disconnect.
